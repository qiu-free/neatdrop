# 离线分类覆盖与文件纳入优化方案

日期：2026-11-04  
性质：验收整改方案，等待产品确认后再拆分为实施规格和代码任务。  
基线：NeatDrop `v0.6.0-library-review`，分类代码与规则以本地仓库为准。

## 一、验收结论

当前症状至少来自三种不同原因，必须分别计数和处理：

1. **格式/安全门槛**：工作台只接受 JPG/JPEG/PNG/WebP 静态图片、文本型 PDF、UTF-8 TXT/Markdown。DOCX/PPTX/XLSX/CSV、扫描型 PDF、HEIC/GIF、子文件夹等会被跳过，不能进入当前选择/审核流程。
2. **分类规则覆盖**：taxonomy 有 9 个主类、57 个子类。按实现中的显式文字规则/用途规则/视觉映射静态盘点，有 45 个子类包含至少一种映射，其中一个是兜底目录“待分类”；排除兜底后，56 个具体用途类中有 44 类具备代码映射、12 类没有独立文字规则或视觉映射：银行材料、缴费凭证、税务材料、研究数据、演示资料、家庭资料、住房物业、旅行资料、照片待细分、图标标志、界面设计、参考素材。它们仍可手动在支持格式的文件详情中选择，但不能期待离线自动建议命中。此映射数量**不表示分类准确率或有效覆盖率**。
3. **证据/引擎限制**：规则由标题、正文及字段锚点触发；文件名只作弱线索。新增的 8 个用途规则始终待复核。数据图表、表格影像、流程图等视觉类型候选尚未校准，不能单凭内容形式决定存档用途。OCR/视觉模型未安装、图像信息不足、PDF无文本层、乱码/截断/读取失败也会限制结果。语义候选默认关闭。

当前开发证据不能证明总体质量：已有的 40 个场景是手写合成开发集；v5 的 88 个用途变体由 8 组相近模板生成；12 份图像记录是既存模型输出重放，没有重新提取。不得将这些数量表述为独立样本量或真实准确率。

按当前默认离线规则/视觉映射静态盘点，覆盖如下。“有映射”仅指分类器代码中存在一种候选产生路径；其中许多只能给候选，且需要实际提取出必要证据。55 个非兜底语义画像标注为 candidate-only，语义引擎默认关闭，因此这些画像本身不会给 55 类带来自动覆盖。

| 主分类 | 有自动候选映射 / 子类总数 | 映射方式概况 |
|---|---:|---|
| 票据凭证 | 5 / 8 | 发票、小票、支付、账单、报销规则；银行/缴费/税务材料缺专用规则 |
| 学习科研 | 9 / 10 | 笔记、课件、论文、试题、板书、图表和三种候选用途；研究数据缺专用规则 |
| 工作办公 | 8 / 9 | 合同、简历、报告、工作记录、表格影像和三种候选用途；演示资料缺专用规则 |
| 活动事务 | 3 / 3 | 通知、报名、会议 |
| 生活服务 | 7 / 10 | 快递、出行票据、订单、医疗、证件和两种候选用途；家庭/物业/旅行资料缺专用规则 |
| 照片影像 | 5 / 6 | 人物、风景、美食、宠物、物品视觉候选；照片待细分无独立映射 |
| 设计娱乐 | 5 / 8 | 海报、插画、壁纸、表情及流程/结构图；图标/UI设计/参考素材无独立映射 |
| 临时资料 | 2 / 2 | 排队取餐、临时状态码 |
| 待分类兜底 | 1 / 1 | 文档影像/截图可以落入兜底，但不表示得出了用途类别 |
| **合计（含兜底）** | **45 / 57** | 36 个子类有文本/用途规则，12 个有视觉标签映射，3 个两者重叠；不能作为准确率解释 |

因此，除兜底以外当前具体用途映射为 **44/56（78.6%）**；其中 12 类为手动选择路径。该覆盖率只统计代码路径，并不代表这些类在实际文件上会触发、识别可靠，或达到发布门槛。

特别要分开“可以进入人工归档批次”与“有自动分类规则”：当前支持的未命中文件仍可手动编辑类别后纳入；超出扩展名白名单的文件连手动归档批次也进不去。这两个入口是本方案要分别验收的事项。

## 二、目标与原则

- **不静默漏项**：每个扫描对象都得到一个明确、可检索的处置状态及原因。文件处置状态与分类标签是两套字段，格式不支持不能伪装成“待分类”。
- **分开“可分析”与“可归档”**：`analysis_supported` 继续只表示现有解析/OCR能力已支持；新增独立的 `archive_eligible` 只针对经批准且可原样安全复制的后缀，不把归档白名单扩展成内容解析白名单。
- **允许有边界的人工纳入**：在安全、允许的扩展名白名单内，可增加“仅手动归类，不读取内容”的副本归档路径。该文件使用者明确选择分类和名称；界面不显示内容预览或自动建议。原文件字节、扩展名、大小限制、哈希校验、固定目标目录及最终计划确认继续执行。
- **未知即复核**：未达到逐类验收门槛时，结果为候选或待分类，不给普通建议；“待分类”是合法的受理结果，不是分类成功率。
- **范围先于准确率**：分别度量可扫描文件、可解析内容、具备规则的子类、给出非兜底建议的文件，明确每个指标的分母。
- **本地数据优先**：标注和评测可在本机完成；未经授权的真实文件、正文或路径不得进入提交、云端请求或默认日志。

建议把状态拆成三个正交字段，避免一个“分类状态”承载多种含义：`intake_status`（是否允许纳入、是否只可手动归档）、`analysis_status`（未分析/成功/失败/未请求及错误原因）、`decision_level`（ordinary/candidate/abstain）。举例：一个获批但无解析器的文件可为 `manual_only + not_requested + abstain`；一个成功读到内容但没命中的 TXT 可为 `supported + completed + abstain`；超过大小限制的图片是 `rejected_size + not_requested + abstain`。转换和统计不得把这些合并成“未分类文件”一栏。

## 三、分类标准与输出契约

每个子类补齐一份统一标准：定义；正例；反例；必要证据；可选支持证据；相邻易混子类；可接受的内容形式；输入覆盖要求；输出等级；是否允许普通建议；未命中时的处置状态。规则锚点与示例来自同一标准文件，避免运行代码、界面说明和评测集各说一套。

| 输出等级 | 进入条件 | 用户界面与后续 |
|---|---|---|
| 普通建议 | 当前内容可解析；类规则已通过独立发布验收；强用途证据和必要字段满足；无冲突、质量闸门或覆盖限制 | 显示类别、原文证据、所用来源和覆盖范围；仍需用户一键审核，执行前仍需确认路径 |
| 候选待复核 | 有真实线索，但证据不足、类规则尚未校准、新用途/视觉形式未校准、类别冲突或读取不完整 | 显示一个主建议和至多两个易混候选；给出逐条原因；允许手动更改或选择“待分类” |
| 待分类/拒判 | 没有足够用途证据、视觉模型不可用且无其他证据、图片信息不足 | 保留原名；允许对可归档项目人工选择已有类别；不得默认为某类 |
| 手动归档（不解析） | 文件属于明确批准的安全扩展名白名单，但暂不支持提取/识别 | 明示“未读取文件内容”；只能人工选择类别/名称；详情不请求解析或预览；进入同一受控计划和确认流程 |
| 未纳入/失败 | 不在批准白名单、目录、链接、读取错误、大小/像素/预算/身份安全限制 | 显示稳定原因码、可采取动作和是否可重试；无分类复选框，不把错误归为待分类 |

UI 建议把分析结果明确标成“内容形式 + 存档用途 + 处置状态”。例如，“看起来是柱状图”是内容形式；“学习科研/数据图表”是用途候选；若缺少研究语境则要求复核。

## 四、实施阶段

### 阶段 0：建立验收基线

先梳理真实抱怨样本对应的扩展名、当前跳过/错误原因、期望用途、现有标签、可用证据和用户最终选择。阶段退出条件是形成处置状态字典、57子类映射差距表、优先样本与分组规范、300–500份开发/校准基线计划、冻结测试集隔离规则。真实资料由用户明确挑选，在本机建立匿名案例清单；源码只保存合成样例和匿名标签。按主类/子类、相邻混淆、文件格式、图像/低质量输入、范围外材料分组，避免同一文档或模板变体跨校准集和测试集。

第一轮盘点并优先研究高频的 10–12 类，而非宣称 57 类全面具备自动识别能力。先建立至少 300–500 份获授权、相互独立的本机资料基线并另留冻结测试集；这只用于定位优先问题，不代表 10–12 类都能自动发布。每类达到普通建议门槛所需的独立正负样本，可能使总量进一步增加。拒绝把模板改写充当独立样本。样本按主类/子类、相邻混淆、文件格式、图像/低质量输入、范围外材料分组，避免同一文档或模板变体跨校准集和测试集。样本不足的类别只能手动归档或待复核。

### 阶段 1：让扫描处置完整可见

为扫描结果定义并测试显式处置枚举，例如 `ready`、`manual_only`、`unsupported_format`、`directory_skipped`、`link_blocked`、`read_failed`、`size_limited`、`empty`、`budget_skipped`。前后端同名展示，不根据自由文本推断；筛选支持“可自动分析 / 可手动归档 / 需处理”。目前扫描最多枚举 2000 项，达到上限时需明确显示“扫描数量上限已达，清单可能不完整”；不能把枚举到的数量说成整个目录总数。汇总按实际清单行计数。任何范围/读取失败需在行内和汇总显示原因及动作。

先实现受控的“安全格式手动归档”薄路径：逐项批准不会被执行的被动资料格式白名单（候选 DOCX、PPTX、XLSX、CSV；应先检查容器/宏等风险，PNG、JPG、WebP、文本 PDF 继续走当前常规分析，扫描型 PDF 单独评估）；只复制原始字节和核对哈希，不启动 Office、不解释宏/公式/嵌入对象，不调用内容解析器。单文件 20 MiB、批次 50 项/200 MiB 与现有路径、链接、身份、复制确认约束继续适用。拒绝可执行文件、未知格式及未经审查格式。扫描型 PDF 只有在另外立项、建立页面/OCR预算和安全解析测试后才加入。

手动归档分支须在后端独立携带 `analysis_mode='manual_only'`，不能被伪装为有模型建议的普通编辑。预览 API、网格缩略图和分析 API 对此分支统一禁止读取；事务日志记明“内容未解析，用户手动选类”。分类和目标名称由用户明确选择，执行器仍用 taxonomy 白名单生成固定目标，不允许自由路径。首版不得对文件内容生成索引、OCR缓存或语义向量。阶段退出条件：扫描总账闭合；自动分析与手动归档两种入口/API权限隔离；手动归档不触发 preview/OCR/模型调用；计划、复制、撤回沿用既有安全语义。上线前由产品确认白名单具体扩展名。

### 阶段 2：修补高优先子类覆盖

以阶段0的频次/损失分析排优先级；首批建议评估：银行/缴费/税务凭证，研究数据与演示资料，旅行/家庭/住房资料，照片待细分，以及图标/界面设计/参考素材。每一类先完善定义、邻类排除、必要证据，再写规则和混淆负例。业务类目用内容锚点+两个独立、非空字段组形成候选；文件名、泛化标题、孤立关键词不够。视觉类目需要独立视觉证据，界面截图不自动推断为 UI 设计，图标外观不推断为创作素材。

每次规则变更同步更新该子类正例、相邻负例、旧版冻结回归和样本来源组；不得只添加正向触发句。新的用途规则先维持 candidate-only，跨独立来源通过质量闸门才允许转换为普通建议。

首版新规则全部 candidate-only；不得仅因规则分数高就切换普通建议。只有阶段3的冻结验收通过后才逐类别开放普通建议。对确有用途但当前没有子类的项目，优先选择现有主分类或待分类，需有多份独立证据证明形成稳定新意图后再增类；禁止一次性把相近概念堆成大量子类。

### 阶段 3：独立评测和分级放量

对每类报告：支持输入数；可解释证据覆盖数；主分类和子分类 Precision/Recall/F1；Top-1/Top-3；相邻类混淆；待复核/拒判率；“待自动建议样本中错误建议率”；普通建议误报；人工改类率；读取失败/不支持率；处理时延和资源。样本按原始文件/来源/近重复组切分，建立冻结测试集；OCR抽取、视觉模型和分类规则分别标版本和指纹。

建议的普通建议起始门槛：某子类冻结测试中至少 50 个独立正例和 50 个独立相邻负例；Precision 点估计不低于 95%，95% Wilson 下限不低于 90%；相邻负例错误归类点估计不超过 5%；无证据、教程/范本/反例与低质输入不能越过复核闸门。另须在两个不同来源组做真实样本复验。任一项未满足则该类保持 candidate-only。这个门槛是方案建议，不是当前实测结果；如样本量/用户风险偏好不同，先调整门槛再冻结评测集，禁止看完测试集后调规则再宣称通过。

### 阶段 4：发布和回归

发布说明逐类列出开放级别和未覆盖边界。合并新支持格式或规则后，运行 API/安全边界测试、全量后端和前端测试、生产构建、合成端到端流程及冻结数据集；确认原件哈希不变、无法解析文件的用户处置正确、结果面板不存在零状态遗漏。真实线上准确率不得由合成结果替代。

每次正式发布形成逐类 go/no-go 表、数据/规则/模型指纹、与冻结版本的差异报告和可回滚版本；未达标子类继续 candidate-only。

### 阶段 5：统计和依据可见

验收报告同时呈现“有多少发现/有多少支持/有多少仅手动归档/有多少因原因未纳入”以及逐类别评测，不只报一个总准确率。工作台需允许按处置状态筛选；拒判、格式不支持和引擎故障拥有各自的可执行建议（选择手动归档、换目录、重新扫描/重试、安装本地能力或留在待分类）。管理视图按冻结分母计算每类证据覆盖、普通建议比例及人工改类率，并清楚标示候选和兜底项目。

## 五、发布验收矩阵

| 维度 | 验收条件 |
|---|---|
| 扫描总账 | 实际枚举的每一项都显示稳定状态；支持、手动、跳过、失败数量之和等于清单行数（应用私有 `.neatdrop` 元数据单列）。达到 2000 项扫描上限时显示清单可能不完整，不声称已扫描完整目录 |
| 文件纳入 | 仅 `analysis_supported` 项进入分析选择器；另外，批准的 `archive_eligible` 项能进入手动归档批次并明确未解析；其他扩展名、链接、目录、越限文件不能进入计划，并给出稳定原因 |
| 类标准 | 每个参与自动建议的子类具备正例、反例、必要字段、混淆对象和质量限制；缺失项不发布普通建议 |
| 可解释性 | 每个非兜底建议展示证据片段、来源（标题/正文/OCR/视觉/语义）、采样范围、匹配状态与复核原因；分数以规则/相似度值展示，不标百分比准确率 |
| 不确定性 | 一类对多个子类接近、用途与图像形式不一致、OCR/采样质量不足、语义与规则分歧时明确降级至候选/拒判 |
| 质量门槛 | 每个开启普通建议的子类各自通过冻结测试门槛；总 Top-1 或合成集表现不替代逐类发布判断 |
| 指标口径 | 同时报候选 Top-3 recall、普通建议 precision/覆盖率、候选/拒判率及不支持率；不得仅报总体 accuracy 或只统计已接受建议 |
| 离线声明 | 全离线流程无网络请求；任何模型未装/校验失败均显式告知并走规则候选或人工处置，不静默云端降级 |
| 文件安全 | 手动归档也复用当前原件保留、固定目标、独占创建、哈希、事务记录、撤回信任和最终确认保证 |

## 六、代码责任范围（实施时）

- `backend/neatdrop/classification_profiles.json`、`taxonomy.py`：标准、必要结构、易混类与能力级别来源。
- `backend/neatdrop/classifier.py`、`decision.py`、`content_quality.py`：规则/视觉证据、明确候选/拒判，按类门槛放行。
- `backend/neatdrop/files.py`、`executor.py`、API 模型与 API 测试：独立表示 `analysis_supported` 与 `archive_eligible`，处理纯复制记录和路径/文件身份校验不变。
- `frontend/src/types.ts`、`fileSelection.ts`、`useWorkspace.ts`、`Workbench.tsx`、`Inspector.tsx`、`api.ts`：扫描处置状态、筛选批次、手动/自动流程和理由解释。
- `docs/evaluation/`、`scripts/evaluation/`：分组本地标注、冻结测试集、逐类指标和可复跑验收报告。

## 七、决定前提

本方案不声称“所有 57 类都能自动精准分类”。推荐目标是：所有已发现文件有明确处置；获准安全格式不能因缺少提取器而完全堵住人工归档；自动建议只为有充足且冻结验收通过的类开放。实施前先确认阶段1要纳入的扩展名白名单与优先分类；其他范围沿用现有安全上限。

本文件只是一份设计方案，不改动分类逻辑、文件接纳逻辑、模型或界面。
