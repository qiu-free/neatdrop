## Task 3 — library frontend and navigation

Reviewed `library-review.patch` (frozen delivery `b715ba9`), the Task 3 delivery report, the complete LibraryPage implementation/tests/styles, App/navigation wiring and the shared API/preview request lifecycle.

**Spec verdict: WITH FIXES. Quality verdict: WITH FIXES.** Current-directory scope, classification/search, list refresh and abort handling, opaque-ID preview requests, unavailable-state explanations, modal semantics, explicit close/backdrop/Escape, background inertness/scroll locking and close-trigger restoration match the design. Each page entry mounts a fresh library; workspace changes reset the keyed content, and history/manual refresh abort the old list. Previews are not cached: switching/closing aborts the old request and each new item starts with cleared state, including rapid A→B→A. The shared two-request budget and local data-image restriction remain in use. One keyboard focus edge needs correction:

- **[P2] Move focus when adjacent navigation disables its own button — `frontend/src/components/LibraryPage.tsx:133`.** Open a library with at least two entries, focus “下一个归档副本”, and activate it to reach the final visible entry (the equivalent issue occurs with “上一个归档副本” at the first entry). The same focused DOM button becomes disabled. LibraryDrawer's mount-only focus effect (`90–118`) does not move focus when `item.id` changes; its focusin guard cannot reliably handle a browser dropping focus to `body` during disabling. Keyboard focus can therefore leave the modal and lose its visible position until another Tab press recovers it. Retain the navigation direction and, after each item change, focus the still-enabled direction, the opposite navigation control or close with `preventScroll`, as Workbench already does. Add a focused endpoint regression for both directions. This finding comes from code inspection; controller browser QA should confirm the browser-specific activeElement behavior while checking the fix.
